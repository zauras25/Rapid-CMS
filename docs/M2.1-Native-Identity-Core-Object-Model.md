# M2.1 — Native Identity & Core Object Model Specification

Status: Draft — Discovery/Requirements
Milestone: M2 — Core Domain Model & Figma-Native Behavior
Sub-phase: M2.1
Implementation Status: Not Started
Freeze Status: Not Frozen

## 1. Purpose

M2.1 defines the foundational identity, ownership, reference,
and core object semantics of the Native Design Domain Model.

The Native Domain Model is the source of truth for design state.

Figma is an interoperability/source concern and must not become
the internal architectural dependency of the Native Domain Model.

## 2. Architectural Boundary

Figma / External Source
    ↓
Compatibility Boundary
    ↓
Native Domain Model
    ↓
Future Core Engines

Native Domain must remain independent from:
- Figma internal object types
- Renderer
- Editor UI
- Storage implementation
- Target framework
- Code generator

## 3. Identity Model

Every first-class entity has a stable native identity.

Required identity types include:

- ProjectId
- DocumentId
- PageId
- NodeId
- ComponentId
- ComponentSetId
- InstanceId
- VariantId
- StyleId
- VariableId
- TokenId
- AssetId
- PrototypeId
- InteractionId
- ReferenceId

Identity requirements:

- Stable throughout entity lifetime.
- Independent from names.
- Independent from hierarchy position.
- Preserved through serialization/deserialization.
- Preserved through recovery.
- Independent from source-system IDs.
- Suitable for deterministic references.

Native Identity != Source Identity

## 4. Entity Semantics

Entities have identity.

Entity equality is based on:
- Entity type
- Native identity

Entities include:

- Project
- Document
- Page
- Node
- Component
- Component Set
- Instance
- Variant
- Style
- Variable
- Token
- Asset
- Prototype
- Interaction
- Reference

## 5. Value Object Semantics

Value Objects have no independent identity.

Equality is based on semantic value.

Expected future value objects include:

- Position
- Size
- Bounds
- Transform
- Color
- Spacing
- Constraint
- Layout configuration
- Typography values
- Reference values

## 6. Project

Project is the top-level isolation boundary.

Project owns or coordinates:

- Documents
- Project-level assets
- Shared styles
- Variables/tokens
- Project metadata

Cross-project references are invalid unless explicitly supported
by a future architecture decision.

## 7. Document

Document is a complete native design artifact.

Document contains or references:

- Pages
- Components
- Component Sets
- Styles
- Variables
- Tokens
- Assets
- Prototypes
- References
- Metadata

Document identity is stable.

Membership and ownership must be explicit.

## 8. Page

Page belongs to a Document.

Page contains a node tree through its root node.

Required semantics:

- PageId
- Document ownership
- Name
- RootNodeId
- Stable identity

A Page must have at most one root node.

Root node ownership must remain within the same document/page boundary.

## 9. Node

Node is the central semantic design object.

Base Node responsibilities:

- Identity
- Name
- Node Type
- Parent
- Children
- Geometry
- Layout
- Appearance
- Metadata
- References

Node is a domain object, not a renderer object or UI object.

## 10. Node Tree Invariants

The node tree must enforce:

- No self-parenting.
- No cycles.
- No duplicate child membership.
- One parent maximum per node.
- Parent/child relationship consistency.
- Deterministic child ordering.
- Project/document boundary integrity.

For every valid relationship:

Parent.Children contains Child
    iff
Child.ParentId == Parent.Id

## 11. References

References are first-class semantic relationships.

Reference contains conceptually:

- Source
- Target
- Relation
- Metadata

References use native identity rather than runtime object pointers.

References must therefore be:

- Serializable
- Deterministic
- Validatable
- Recoverable

## 12. Referential Integrity

A valid reference must resolve to an existing valid entity
within the permitted ownership boundary.

Invalid state:

Reference → Missing Entity

must be detectable by domain validation.

Reference creation and reference validation may be separate
responsibilities, but invalid references must not silently become
accepted valid domain state.

## 13. Source Identity

External source identity is separate from native identity.

Conceptual model:

Native Entity
    +
Compatibility Metadata
        ↓
External Source Identity

Figma IDs must not become the primary Native Domain identity.

## 14. Metadata

Metadata is separated into:

- Native Metadata
- Compatibility Metadata

Figma-specific information must not leak into core semantic
properties without an explicit architectural decision.

## 15. Serialization

Native identity and ownership semantics must survive:

Native State
    ↓
Serialize
    ↓
Deserialize
    ↓
Equivalent Semantic State

The following must remain stable:

- Native IDs
- Ownership
- Parent/child relationships
- References
- Entity relationships

## 16. Determinism

The same valid state and same deterministic operation must produce
the same semantic result.

Uncontrolled nondeterminism in:

- IDs
- ordering
- relationships
- serialized state

is prohibited where deterministic behavior is required.

## 17. Recovery Compatibility

Identity semantics must support future soft-delete/recovery.

Deletion:

Entity
    ↓
Soft Deleted

Recovery:

Soft Deleted
    ↓
Restored

Restoration must preserve Native Identity.

Actual deletion/recovery engine behavior is outside M2.1 scope.

## 18. Figma Leakage Prohibition

The Core Domain must not depend on Figma-specific internal classes.

Forbidden architectural dependency pattern:

Core Domain
    ↓
Figma Internal Model

Required pattern:

Figma Compatibility
    ↓
Native Domain
